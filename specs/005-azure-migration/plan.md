# GMG Agent Azure migration plan

November 20, 2026 · USD retail estimates before grant

## Recommendation

Start with one **Azure Container App on the standard Consumption profile** in **West US 3**, two containers in the same replica, **Hot LRS Blob Storage**, and **one Fireworks Nemotron pay-per-token deployment** in East US, US Data Zone Standard, subject to confirmation of all three nonprofit grant meters in billing case 2611200010002566. Start at zero minimum replicas and one maximum replica. Retain Next.js, FastAPI, and the existing retrieval code. Keep Nemotron on the Mac as the development baseline and temporary rollback path. The model comparisons below record earlier pilot estimates.

| Component | Current behavior | Proposed Azure setup |
| --- | --- | --- |
| Web and sign-in | Next.js on Vercel with LinkedIn OIDC and server-side JWT session checks | Next.js standalone Node container. Public HTTPS ingress serves port 3000. |
| API and retrieval | FastAPI on the Mac, proxied through ngrok, in-memory text and evidence indexes | FastAPI sidecar bound to `127.0.0.1:8000`. The Node server proxies same-replica requests with the existing internal bearer token. No extra ingress port. |
| Inference | Nemotron 3.5 Lightning via Ollama. People matching makes one call to interpret and up to one to rank. | Hosted Nemotron through Microsoft Foundry with bounded requests, schema validation, deterministic retrieval, and a persistent allowance. |
| Data | AlmaShines snapshot, Bay Area enrichment sidecar, manually reviewed additions, separate sign-in allowlist | Private Blob container for minimized, versioned data. Keep the allowlist in an Azure secret. Use one small Table Storage table for the inference budget. |
| Image storage | Current releases built and staged locally | Prefer private GitHub Container Registry images if GMG approves the package ownership and narrowly scoped pull credential. Its container storage and bandwidth are currently free. Use Azure Container Registry Basic if GMG needs identity-only registry access or Azure-only ownership. |

Begin with **0.5 vCPU / 1 GiB total** across the two containers. Measure realistic boot, memory, and concurrent requests before selecting final sizing. Increase by one Consumption size step only if measurements justify it. The raw snapshot is about 9.2 MiB, but the processed Python index and both runtimes drive memory needs. Quota, model availability, and agreement terms must be checked on GMG’s subscription. East US 2 is a fallback region with the same checked compute rates. Standard Consumption supports the shared replica, managed certificates, and revision rollback. Container Apps Express uses similar consumption pricing but lacks sidecars, managed custom-domain certificates, and multi-revision traffic switching. App Service Free has shared CPU quotas that can stop the app until reset, and the GMG subdomain would require moving to a paid tier. Static Web Apps plus Functions warrants revisiting if measured serving costs justify moving the authenticated Next.js and FastAPI routes. First measure whether separate Consumption apps would save compute by letting FastAPI stay asleep during frontend-only visits. Defer database hosting, vector search, and always-on GPUs until a measured need warrants them. ## Cost model and limits

West US 3 retail meters checked November 20 show active CPU at $0.000024 per vCPU-second, memory at $0.000003 per GiB-second, and requests at $0.40 per million above the free allocations. Monthly grants are 180,000 vCPU-seconds, 360,000 GiB-seconds, and 2 million requests per subscription. At 0.5 vCPU and 1 GiB, compute has about 100 active replica-hours within an otherwise unused monthly allocation. Include starts, cooldowns, rollback revisions, and other Container Apps sharing the subscription. ACR Basic is $0.1666/day, or about $5 for a 30-day month. Hot LRS Blob capacity is around $0.0184/GB-month at the checked low-usage tier, plus transactions. ## Data and access boundaries

- Build an allowlisted projection locally after applying approved enrichment and directory additions. Preserve stable IDs, display name, approved city/region, role and professional evidence, normalized LinkedIn URLs and source labels, and the job fields consumed by search and rendering. Preserve existing aggregate statistics using flags such as has-photo, without carrying an unused photo URL. Review free-text job and member evidence for hidden contact details before upload. Keep raw member emails, phones, addresses, birthdates, demographics, workbooks, session data, and the allowlist out of the Blob dataset, model prompts, and container images.
- Publish verified versions as immutable Blob objects with checksums and a small manifest. Read one validated version into memory at startup with managed identity, keep the last two approved versions, and rehearse reversing the manifest or rolling back to the previous revision. Treat a missing, invalid or unexpectedly empty snapshot as unready. Begin with a manual refresh from the source operator. A low-frequency Container Apps Job can replace it after GMG confirms the refresh process, its credentials, and costs.
- Use Azure RBAC for Blob reads, quota-table writes, and Azure OpenAI calls. Scope the publishing identity separately. Store the LinkedIn client secret, session secret, internal API token, and approved email list as secret references. Disable anonymous Blob access and avoid broad permissions. Preserve the verified-email check and the subject match for LinkedIn userinfo. Disallow unapproved CORS origins and never expose FastAPI, an internal credential, or a paid-model endpoint to the browser.
- The public remote’s `origin/master` tree includes a historical `.env.local`. Its local HEAD version has populated `NEXTAUTH_SECRET` and `GITHUB_CLIENT_SECRET` fields. Credential validity remains unverified. Work with the owners to rotate any still-valid credentials, confirm the production app’s authentication after rotation, and establish a clean, pinned source baseline before building Azure images. Preserve unrelated local changes and use an allowlist of files for the release.
- Keep prompt data minimal. Use only request text needed to interpret intent and a bounded set of anonymized candidate IDs with approved professional excerpts for ranking. Scrub direct contact details from inference inputs. Render identities and profile links locally. Use stateless requests and disable application logging of prompt and response text. Review Microsoft’s abuse-monitoring and data-processing terms before sending live member evidence. [Managed model access](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agent-permissions#account-level-access) · [Foundry privacy](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/openai/data-privacy)

## Local Azure emulation

Azure has service-specific emulators. **Azurite** covers the Blob, Queue, and Table APIs, so it can exercise GMG’s snapshot fetch, version rollback, and budget concurrency tests from local Compose. Run Next.js and FastAPI in the same local topology, use local Ollama for model behavior, and add a stub for Azure response contracts, quota errors, timeouts, and malformed outputs. Foundry Local is an optional on-device OpenAI-compatible endpoint. Validate hosted GPT-6 Luna separately in Azure. Azure Functions Core Tools is useful if Phase 2 ever needs Functions. Real Azure is still needed for RBAC, actual LinkedIn callback handling, ingress, TLS, scale-to-zero, model behavior, and the invoice. [AWS Emulator](https://docs.aws.amazon.com/emulator/latest/userguide/) · [Azurite](https://learn.microsoft.com/en-us/azure/storage/common/storage-install-azurite) · [Foundry Local](https://learn.microsoft.com/azure/foundry-local/what-is-foundry-local) · [Functions local runtime](https://learn.microsoft.com/en-us/azure/azure-functions/functions-develop-local)

## Release and rollback

1. **Baseline and local proof.** Freeze the live data version and auth expectations. Prepare clean source and rotate applicable credentials. Build both images locally, test Azurite and Ollama, and validate the proposed Bicep deployment with what-if once access is available.
2. **Small Azure pilot.** Use Azure’s generated hostname, a tightly limited test allowlist, a minimized real snapshot once approved, and a single small Azure-sold model deployment. Add the exact HTTPS LinkedIn callback for this host while retaining the existing Vercel callback. Use a separate session secret. Test an approved account and an unapproved one. Verify the model metering against the grant-bearing scope.
3. **Compare under load and failure.** Run real-browser desktop and mobile checks. Test scale-from-zero and simultaneous requests, validate profile and job rendering, and simulate throttling, model failure, storage access loss, bad snapshots, and quota exhaustion. Record model latency and spend without recording private prompts. Rehearse rolling back the data and the app independently.
4. **Cut over.** Bind the GMG subdomain and its managed TLS certificate if DNS access is available. Register the exact final LinkedIn callback and test it directly. Keep the old Vercel deployment and Mac/ngrok path available during a proposed seven-day observation period. Share the Azure URL after the release checks. The existing `vercel.app` hostname can later redirect normal entry traffic through Vercel, subject to its hosting terms. Users sign in again on the new host. [Azure managed certificates](https://learn.microsoft.com/en-us/azure/container-apps/custom-domains-managed-certificates) · [LinkedIn OIDC](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/sign-in-with-linkedin-v2)
5. **Rollback and retire.** On a verified access regression, wrong results, or unexpected billable meters, restore the last tested Azure revision or data manifest first. If Azure cannot serve, restore the previous Vercel entry point backed by the Mac with valid credentials. Once the Azure path has passed the observation window and the rollback rehearsal, remove temporary deployments and the tunnel from routine service.

Proposed pilot latency targets are a warm exact search within 1.5 seconds at p95, a warm model-assisted search within 12 seconds at p95, and a cold first completed request within 25 seconds. Track time to first response separately from time spent in Azure inference. Make readiness depend on the validated directory and both app processes. Keep model availability outside readiness checks so a model outage does not take down the directory. Measure and tune image size and startup work before paying for a warm replica. Use platform metrics and short, redacted on-demand diagnostic logs during the pilot.
