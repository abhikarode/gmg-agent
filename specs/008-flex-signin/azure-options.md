## How Azure apps handle the browser handoff

1. **One application origin.** The application starts OAuth and receives the callback on its own origin, exchanges the provider code server-side, verifies the session, and returns a redirect to the app. Azure Container Apps Easy Auth supports custom OIDC and can own this callback. The existing NextAuth path is another implementation of the same shape. GMG still needs to enforce verified email and active membership server-side. Moving this callback to Container Apps would put its wake-up back on the sign-in path. Easy Auth compatibility with LinkedIn's claim and token behavior needs a real test. [Container Apps authentication](https://learn.microsoft.com/en-us/azure/container-apps/authentication), [Custom OIDC in Container Apps](https://learn.microsoft.com/en-us/azure/container-apps/authentication-openid), [OAuth security best practices](https://www.rfc-editor.org/rfc/rfc9700.html)
2. **One public origin with path routing.** Azure Front Door can serve the static landing, auth paths, and Desk paths under one hostname while routing each to its own backend. The app can issue a host-scoped session cookie on that hostname. Auth and personalized responses must bypass edge caching. Front Door Standard has a $35 monthly base before requests and traffic. The edge does not keep the origin workers warm. [Front Door routing](https://learn.microsoft.com/en-us/azure/frontdoor/front-door-route-matching), [Front Door pricing](https://azure.microsoft.com/en-us/pricing/details/frontdoor/)
3. **Managed Static Web Apps authentication.** Custom OIDC and bring-your-own API routing require Standard. The linked integration permits one `/api` backend per environment and has a 45-second request limit. Hybrid Next.js preview excludes linked APIs to Flex and Container Apps. GMG would need a frontend and API redesign to fit that hosting model. [Custom authentication](https://learn.microsoft.com/en-us/azure/static-web-apps/authentication-custom), [API limits](https://learn.microsoft.com/en-us/azure/static-web-apps/apis-overview), [Hybrid Next.js support](https://learn.microsoft.com/en-us/azure/static-web-apps/deploy-nextjs-hybrid)
4. **An identity broker or an API gateway.** Entra External ID can federate a custom OIDC provider and map a verified email claim. This adds an external tenant, user flow and new callback. LinkedIn compatibility with the broker's token and claim handling still needs validation. APIM Consumption has a low-traffic request grant and can put APIs behind one hostname. Using it for this Desk would require validating browser redirects, session cookies and dynamic app routes. Neither service keeps the Container Apps replica warm. [Entra custom OIDC](https://learn.microsoft.com/en-us/entra/external-id/customers/how-to-custom-oidc-federation-customers), [APIM pricing](https://azure.microsoft.com/en-us/pricing/details/api-management/)
5. **Automatic form POST across origins.** OAuth defines an auto-submitted form as a way to pass authorization results through a browser body. This is the closest standard pattern to GMG's current Flex-to-Desk exchange. It keeps the short-lived relay code out of URLs. A visible submit button adds a second action and lets the same code be submitted again. GMG can retain the existing services and the single-use code by submitting once automatically and restarting the existing same-origin LinkedIn flow if the exchange fails. [OAuth Form Post Response Mode](https://openid.net/specs/oauth-v2-form-post-response-mode-1_0.html), [OAuth security best practices](https://www.rfc-editor.org/rfc/rfc9700.html)

For the pilot, use the automatic handoff on the existing services and treat warm capacity as a separate latency decision. Keeping Flex warm can reduce authentication and roster startup. The Desk still has its own startup time. A single-origin callback is the simpler long-term flow if sign-in reliability remains an issue after testing the handoff across browsers and startup conditions.
